**Channel access gate** = `chat_access($cid,$profile_id)` (sub_default.php ~285): type1 channel = all staff; type2 = leaf-only dept match (`(int)trim(list_department_id,'|') == myDept`). Every send/history handler calls it for the ACTING channel.

**KNOWN GAP (reply/quote feature, Đợt 2):** `chat_reply_snippet($replyToId,$pmap)` (~358) fetches parent via `(new ChatMessage())->getOne($replyToId, fields)` = **pure pkey lookup, NO channel_id constraint**. getOne convention across codebase = by pkey only (verified: Profile getOne calls at 128/296/502). So a reply_to_id pointing at a message in a channel the sender CANNOT read still renders that message's sender-name + 80-char/`[Hình ảnh]` preview back to the sender → cross-channel content/sender disclosure. Two vectors: (1) crafted reply_to_id in POST, (2) stale `this.replyTo` in JS carried across channel switch — `cancelReply()` is NOT called in `openChannel`/`switchTab`/`close` (only on send-success + X button). Fix = pass acting `$cid` into snippet, constrain `getOne`→`getByCond("message_id=.. AND channel_id=..")`, AND reset replyTo on channel switch.
